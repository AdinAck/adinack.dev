## Solution

My project is called **M**emory-mapped **I**/**O** **M**odelling **L**anguage (MIOML). A bit of a mouth-full but, it
gets the job done. A realization I had that took me a long time to come to terms with, was that the solution is *not*
to generate nor verify HALs. But to introduce a layer *before* the HAL that HALs may inherit safety guarantees from.

This layer is already present for many (all?) existing Rust HALs, and at the beginning of my research I contributed to
this layer (generated by [svd2rust](https://github.com/rust-embedded/svd2rust)) as I thought I could simply *improve*
svd2rust. This ended up not being the case, as the SVD files themselves contain insufficient information to model with.

So I'm making a new language for describing a device's peripherals, which I guess will have the file extension `.mioml`.

Let's take a peak at what it looks like:

### Modelling Language

> I have already made a tree-sitter module for syntax highlighting and a fully functioning LSP, niether of which I have
> time to figure out how to embed in this site, so please use your imagination for the colors!

```txt
peripheral gpio {
    /// *Note: It is recommended to set PB8 to a different mode than the
    /// analog one to limit the consumption that would occur if the pin is
    /// left unconnected.*
    register #moder.moder reset 0xffffffff
    register #otyper.otyper reset 0
    register #ospeedr.ospeedr reset 0x0
    register #pupdr.pupdr reset 0x0
    register #idr.idr
    register #odr.odr
    register #afr.afrl
    register #afr.afrh
}
```

This is a description for a single GPIO IP used amongst various STM32 families. Each GPIO instance, of course, is
slightly different from the others in a few ways, so let's look at how they are instantiated for a common G4 model, for
example:

```txt
device g4 {
    schema #rcc.en
    schema #moder.mode
    schema #otyper.ot
    schema #ospeedr.ospeed
    schema #pupdr.pupd
    schema #odr.level
    schema #afr.afsel
    // more...

    peripheral #rcc_g4 as rcc

    peripheral #gpioa @ 0x4800_0000
        requires rcc.ahb2enr.gpioaen.Enabled

    peripheral #gpiob @ 0x4800_0400
        requires rcc.ahb2enr.gpioben.Enabled

    peripheral #gpio as gpioc @ 0x4800_0800
        requires rcc.ahb2enr.gpiocen.Enabled

    peripheral #gpio as gpiod @ 0x4800_0c00
        requires rcc.ahb2enr.gpioden.Enabled

    peripheral #gpio as gpioe @ 0x4800_1000
        requires rcc.ahb2enr.gpioeen.Enabled

    peripheral #gpio as gpiof @ 0x4800_1400
        requires rcc.ahb2enr.gpiofen.Enabled

    // more...
}
```

As you can see, the `#`s indicate some kind of inheritance. They are called *templates*, which describe a base IP that
may be extended for each instantiation. So we are using the previously shown gpio peripheral definition as a template.

Each peripheral expresses a `requires` property which in technical terms defines the *ontological entitlement space* of
the peripheral. In simpler terms, the peripheral is only available for use if the listed field inhabits the listed
variant. MIOML models leverage what I call **entitlements** like these almost everywhere, they are the core of the
novelty of MIOML that introduce the invariants which allow for so much static analysis to be done. We can talk about
this in great detail whenever you like, but I hope the big picture will become clear by the end of this document. The
[entitlements](https://github.com/AdinAck/proto-hal/blob/main/model/src/entitlement.rs) module is the place to look to
learn more, but it is not well documented, a lot of set theory stuff.

Now to go the other direction, let's see what it looks like inside the `moder` register which is present in `gpio`:

```txt
schema mode {
    variant Input ~ 0
    variant Output ~ 1
    variant Alternate ~ 2
    variant Analog ~ 3
}

register moder @ 0x0 {
    store field array mode[0..=15] @ [0..=1, ...] assumes mode
}
```

There are a few interesting things here. Firstly, the fields are called "store". Not "read", not "write", but
*store*. Store is *like* "read" or "write" in the sense that it describes how the field is used, but it expresses some
additional information that is normally either misrepresented or unutilized altogether by existing peripheral access
designs.

In *Rage Against the State Machine*, I was very happy to see that you treated memory as a *boundary* between the CPU
(software) and peripherals (hardware), it took me quite a long time to fully internalize that relationship. It is an
important one from which we can find that fields are more than just "read" or "write", there are acutally **five** of
what I call **access modalities**. This concept is fairly well documented
[here](https://github.com/AdinAck/proto-hal/blob/main/model/src/field/access.rs).

The fields also `assume` the schema `mode`. This is basically expressing that these fields refer to the schema `mode` to
define what values/states the fields may inhabit. This is extremely useful for generating unified types which are used
to enforce the MIOML rules (which we will see soon).

For comparison, fields may define their variants ad-hoc like so:

```txt
read field rrdy @ 31 {
    /// No new data in output register.
    variant NoData ~ 0
    /// [`rdata`](super::super::rdata) contains a result.
    variant Ready ~ 1
}
```

> From cordic::csr.

MIOML performes a plethora of validation steps on the model to ensure it satisfies the rules. Here's an example
diagnostic emitted when the model has a mistake:

```txt
error[E1001]: fields `arg` and `arg0` overlap, occupying 0..=15
    ╭─[ peripherals/cordic.mioml:116:27 ]
    │
116 │ write field arg @ 0..=31
    │                   ───┬──
    │                      ╰───── this domain
    │
117 │     requires cordic.csr.argsize.Q15
118 │
119 │ write field arg0 @ 0..=15
    │                    ───┬──
    │                       ╰───── overlapping domain here
    │
    │ note: overlapping fields have non-trivial intersecting ontological entitlement spaces
    │       [cordic::csr::argsize::Q15] and [cordic::csr::argsize::Q15,
    │       cordic::csr::nargs::One]
────╯
```

In this case, two fields `arg` and `arg0` are what I call **superpositioned**. Field superpositioning is when multiple
fields *physically* occupy overlapping regions of a register (in this case `0..=31` overlaps with `0..=15`). This is
a surprisingly common occurrence in peripherals, and as far as I know has never been modelled properly before.

This diagnostic is telling us that the fields have ontological entitlement spaces that *intersect* (in other words,
do *not* contradict) meaning the model is expressing that there exists a state set of the fields `cordic.csr.argsize`
and `cordic::csr::nargs` where *both* fields exist, hence the error. In this case, the author accidentally listed `Q15`
as the entitlement of field `arg`, when they intended `Q31`, which resolves the error.

### Usage

Let's use the interface generated by MIOML to turn on an LED with the GPIO peripheral.

Skipping some details, here's where we're starting.

```rust
use stm32_spa as hal; // "SPA" stands for "safe peripheral access", subject to change. HAL is also not what this is.

fn main() {
    let p = unsafe { hal::assume_reset() }; // "p" holds a structure that represents the reset state of all peripherals.
    
    // TODO...
}
```

Turning on an LED (a pin) is pretty simple, just put the pin into output mode and set the output to `1`.

```rust
use stm32_spa as hal;

fn main() {
    let p = unsafe { hal::assume_reset() };

    // this is called the modify "gate" which does a read-modify-write on the specified fields.
    // MIOML generates many different gates (modify, write, read, etc.) bespoke to each model.
    // since we are passing the field bindings by value, they are *moving* through the gate, where their types are
    // transformed to reflect the new field states.
    let (new_mode5, new_odr5) = hal::modify! {
        gpioa {
            moder::mode5(p.gpioa.moder.mode5) => Output,
            odr::od5(p.gpioa.odr.od5) => High,
        }
    };
}
```

Of course, this code is making a big mistake. It never enables the clock source to the GPIOA peripheral. So let's see
what happens when we compile it:

```txt
error[E0609]: no field `moder` on type `stm32_spa::gpioa::Masked`
  --> tests/gpio.rs:29:38
   |
29 |                 moder::mode5(p.gpioa.moder.mode5) => Output,
   |                                      ^^^^^ unknown field

error[E0609]: no field `odr` on type `stm32_spa::gpioa::Masked`
  --> tests/gpio.rs:30:34
   |
30 |                 odr::od5(p.gpioa.odr.od5) => High,
   |                                  ^^^ unknown field
```

The type of `gpioa` is `Masked`, so it doesn't have the registers or fields available. In order to make them available,
we use `hal::unmask!`:

```rust
use stm32_spa as hal;

fn main() {
    let p = unsafe { hal::assume_reset() };

    let gpioa = hal::unmask!(gpioa(p.gpioa));
    
    let (new_mode5, new_odr5) = hal::modify! {
        gpioa {
            moder::mode5(gpioa.moder.mode5) => Output,
            odr::od5(gpioa.odr.od5) => High,
        }
    };
}
```

```txt
error: [E2000] provided fields [] are insufficient to satisfy entitlement spaces [{ {<gpioaen | Enabled>} }], which are
       imposed by peripheral "gpioa"
  --> tests/gpio.rs:27:34
   |
27 |         let gpioa = hal::unmask!(gpioa(p.gpioa));
   |    
```

The model knows that in order to unmask the GPIOA peripheral, we must *prove* that the clock source is enabled. The
diagnostic tells us not only which field is required, but what variant it must occupy.

So let's fix it:

```rust
use stm32_spa as hal;

fn main() {
    let p = unsafe { hal::assume_reset() };

    let gpioaen = hal::modify! {
        rcc::ahb2enr::gpioaen(p.rcc.ahb2enr.gpioaen) => _ // type is inferred to be "Enabled"
    };

    let gpioa = hal::unmask! {
        gpioa(p.gpioa),
        rcc::ahb2enr::gpioaen(gpioaen),
    };
    
    let (new_mode5, new_odr5) = hal::modify! {
        gpioa {
            moder::mode5(gpioa.moder.mode5) => Output,
            odr::od5(gpioa.odr.od5) => High,
        }
    };

    // more...
}
```

And this works!
